Ninth Circuit Asylum Pipeline

Two open intern projects

This repository reads every opinion the Ninth Circuit publishes, flags the asylum cases, and extracts 70+ structured legal features from each one — every feature paired with the verbatim quote that supports it. Two projects are open on top of that corpus: one is a measurement study headed for publication, the other is a retrieval system that needs to become trustworthy enough for a practicing attorney.

  • 5,779 asylum cases extracted
  • 70+ features per case
  • $0 /mo running cost
  • runs daily, unattended

Research track

Do language models read asylum law the way a human does?

pipeline maintenance + the extraction-validation study

Empirical research on immigration adjudication has always been bottlenecked on the same step: someone has to read the opinions. Coding a few hundred decisions for “was a credibility finding made?” or “did the court find the required nexus to a protected ground?” is weeks of trained human labor, which is why most studies in this area rest on small hand-coded samples. A language model can obviously produce those labels in seconds — the open question is whether the labels are right, how small a model can get before they stop being right, and whether the machine can be trusted on the legally subtle features rather than just the easy bookkeeping ones. This project is the experiment that answers that, and the validation study it produces is intended for publication.

The design is already in place. Eleven binary features are defined identically for the machine and for the human — the same wording serves as the labeler's codebook and is compiled into the model prompt. Thirty curated opinions, stratified across published/unpublished and granted/denied/remanded, run through a sweep of models spanning three orders of magnitude in size (Llama 3.2 1B and 3B, Phi-4-mini, Llama 3.1 8B, Llama 3.3 70B, Mistral Large 3 675B), each returning all eleven booleans plus an evidence quote in one structured call. Human labelers are coding the same thirty cases by hand. Scoring is per model, per feature: accuracy, F1, and Cohen's κ against the humans. Everything is tracked in git rather than an external service, so the commit SHA on a results file pins the exact prompt and feature definitions that produced those numbers.

Real findings are already sitting in the raw output, waiting for someone to chase them down — and the other half of the job is keeping the machine that produces the data healthy, because a paper about a pipeline is only as good as the pipeline. The daily fetch → classify → extract jobs run unattended on GitHub Actions and they do break: extraction gets cancelled at the 60-minute job timeout mid-batch, the weekly evaluation dies on a single unretried API error, and the court's website is a scraping target that changes without warning.

Where you'd start

  1. Land the human gold standard and run the scoring script for the first time — today it degrades to prediction-only diagnostics because there is nothing to score against.
  2. Add a second labeler on an overlapping subset, so we can report inter-annotator agreement next to model-vs-human agreement. A model that matches humans as well as humans match each other is a far stronger claim.
  3. Fix the small models' JSON failures (retry, repair, or constrained decoding) and report the failure rate as a result — “how small can you go” is a headline finding, not a footnote.
  4. Harden the daily jobs: backoff on every model call, batch sizes that finish inside the timeout, and an alert when a scheduled run fails instead of failing silently.
  5. Once the thirty-case validation holds up, scale the validated features across all 5,779 cases and report prevalence with honest uncertainty.

Systems track

Making legal retrieval trustworthy enough for an attorney

retrieval, evaluation, and the last mile to production

An immigration attorney holding a client's fact pattern wants the same two things every time: which Ninth Circuit cases look like this one, and what did the court actually say. That is a retrieval problem with an unusually low tolerance for confident nonsense — a citation to a case that does not say what the answer claims is worse than no answer at all. The repo has a working system aimed at it: dense retrieval over page-aware chunks, a cross-encoder reranker, a BM25 sparse hybrid so that literal terms like a country name or a docket number aren't buried under merely topical matches, deduplication to one result per case, a refusal threshold for out-of-corpus questions, and a 70B model writing answers whose [N] citations resolve back to a specific page of a specific opinion. It's deployed, it's public, and it evaluates itself weekly.

It is also, by its own measurements, not good enough yet — which is the interesting part. The refusal threshold, the hybrid blend weight, the chunk size and k were all set by reasonable rule of thumb and have never been tuned against labeled data; the ablation scaffolding exists in the harness and has never been run. Your project is to close that gap and prove you closed it, which makes the evaluation as much the subject as the retriever: twenty questions scored by a single LLM judge cannot reliably detect a five-point improvement, and validating that judge against human ratings is its own piece of research — one that connects directly to the gold-standard work in the other project.

The constraints are what make it engineering rather than a hyperparameter grind. The whole system runs on free tiers: the backend has 512 MB of RAM and falls asleep after fifteen idle minutes, the vector index ships inside the git repo, and a 200× corpus expansion has to fit in that budget — so going from thirty cases to the full corpus is a genuine design problem (persist the sparse index? move it to SQLite FTS5? drop it?), not a re-run. Latency is the other honest failure: nobody waits 110 seconds for an answer.

Where you'd start

  1. Fix the weekly evaluation so it stops dying on a transient API error and produces a trustworthy time series — you cannot improve what you cannot measure.
  2. Grow the question set past twenty, add human ratings for a subset, and check whether the LLM judge actually agrees with people before trusting a single one of its verdicts.
  3. Run the ablations already scaffolded in the harness — chunk size, k, refusal threshold, hybrid weight — and report them as a table instead of a rule of thumb.
  4. Make citations strict: have the model cite only what each claim rests on, then verify every citation post-hoc and drop the ones that don't hold up.
  5. Scale the index toward the full corpus inside the 512 MB ceiling, measuring what recall, latency, and memory actually do as N grows.
  6. Stream the answer as it's generated, and go after that 95th-percentile latency.

python3 -m venv ninthc && source ninthc/bin/activate
pip install -r requirements.txt
cp .env.example .env        # NVIDIA_API_KEY, SUPABASE_URL, SUPABASE_SECRET_KEY
git lfs install && git lfs pull   # retrieval project only: pulls the vector index

Start with README.md for the pipeline, design-and-evaluation.md for the retrieval system, and Publications/experiment_01_tracking_plan.md for the study.

One hard rule on the research track: the human gold-standard labels must never be produced with the help of any language model. They are the measuring stick the entire study depends on — labeling with an LLM would quietly invalidate every number in the paper.
